# ルール解説（`/rules/`）の作り直し — 方針と決まりごと

男子新体操のルールを、**何も知らない人が読んで分かる**ところまで書き下ろす。
公式の規則集を写したページ（いまの `/rules/`）は捨て、ゼロから書いた解説書に置き換える。

このファイルは**作る前に決めておく決まりごと**を置く場所。
`../../imrg-hub/` で始まるリンクは、隣のリポジトリー（`~/imrg/imrg-hub/`）を指す。
個別の作業は [TODO.md](TODO.md) に番号で足す。実装の判断で迷ったら、まずここへ戻る。

---

## 1. なぜ作り直すのか

いまの `/rules/` は、公式規則集の条文をそのまま写したもの（本文20万文字）。
2026-09-26に**協会の著作物を使う形は取らないと決めた**ため、このまま公開する道は無くなった。

一方で、作り直す理由は制約だけではない。**いまの形では、そもそも読者に届かない。**

| いまの形の問題               | 何が起きているか                                                                                         |
| ---------------------------- | -------------------------------------------------------------------------------------------------------- |
| 冊子の章立てのまま           | 「1 競技規則」から始まり、最初に読むのが大会運営の手続き。**新体操を知らない人が1行目で落ちる**          |
| 知っている前提で書かれている | 条文は「徒手」「難度」を説明せずに使う。読者が前提を持っていない                                         |
| 重要でない節が大半           | 審判の資格・登録手続き・アンチドーピング規程まで全部入っている。**読者が必要としているのは点の決まり方** |
| 1ページに全部                | 目的の違う読者（言葉を知りたい人／観戦する人／選手）を1枚で相手にしている                                |

## 2. 目指すもの

**小学生が読んで分かる。** これを唯一のゴールにする。

- 公式規則集の**代わりではなく、入口**にする。正確さで競わない。分かることで競う
- **概要から深掘りへ**。上の層は短く言い切り、下の層で詳しく書く
- 副産物として**本の原稿になる**形で書く（→ [8. 1つの原稿から3つの出口へ](#8-1つの原稿から3つの出口へ)）

## 3. 越えてはいけない線

2026-09-26に委員会の斉藤さんへ伝えた3つの約束。**これは守るだけでなく、機械で守らせる。**

| 約束                                                       | 実装でどう守るか                                    |
| ---------------------------------------------------------- | --------------------------------------------------- |
| 協会と男子新体操委員会の名前を出さない                     | 禁止語を CI で検出して落とす（→ 3-2）               |
| 公認でも推奨でもなく、個人が作ったものだと書く             | 全ページ共通の断り書きを**型で必須**にする（→ 3-3） |
| 規則集の条文・表・図を使わない。正式な判断は公式の規則集で | 同上。加えて既存データを退避する（→ 9）             |

### 3-1. 書けるもの・書けないもの

著作権が守るのは**表現**で、ルールそのものではない。この線を作業者が毎回迷わないよう固定する。

|             | 例                                                                                          | 扱い                                              |
| ----------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| ✅ 書ける   | 難度の値（A=0.1／B=0.2／C=0.3／D=0.5／E=0.7）、技の名前、演技時間、演技面の広さ、減点の点数 | **事実・数値は保護されない。** そのまま書いてよい |
| ✅ 書ける   | 「難度は高いものから3つだけ数えられる」といったルールの仕組み                               | 仕組みはアイデア。自分の言葉で説明する            |
| ✅ 書ける   | 自分で撮った映像・写真から描いた図                                                          | 完全に自作                                        |
| ❌ 書けない | 条文の文を写す、言い換える程度で載せる                                                      | 表現の複製・翻案                                  |
| ❌ 書けない | 冊子の表をそのまま再現する（並び・列・まとめ方まで同じ）                                    | 選択と配列に著作権がある（編集著作物）            |
| ❌ 書けない | 冊子の線画を見て描いた図                                                                    | トレースは翻案。**見た目が違っても同じ**          |
| ❌ 書けない | 条文の並び順をそのまま使った章立て                                                          | 同上                                              |

**とくに間違えやすい2つ。**

1. **「形が変わっていれば大丈夫」ではない。** いまの棒人間について、[stickFigure.ts:11-15](../web/src/entities/rule/model/stickFigure.ts#L11-L15) にこう書いてある。「冊子の線画を1枠ずつ見て写し取ってある」「線画の特徴が出るところまで座標を寄せてある」。似せに行った結果ズレているだけなので、**使えない**
2. **数値そのものは自由に書ける。ただし表の形をそのまま使えない。** 難度の値は事実だが、
   冊子と同じ区切り・同じ列・同じ順で並べると表ごと写したことになる。
   **自分の切り口で組み直す**（→ 6-3）

### 3-2. 禁止語を CI で落とす

`web/src/entities/ruleGuide/` 配下の本文に、次の語が入っていたらビルドを落とす。

```text
日本体操協会 / 体操協会 / 男子新体操委員会 / 委員会 / 公認 / 推奨 / 公式規則 / 規則集より
```

- 置き場所は `web/tests/unit/entities/ruleGuide/forbiddenWords.test.ts`（テストとして落とす。CIの `verify` に乗る）
- 例外を作りたくなったら、**例外を作らずに文を書き換える**。「公式の規則集」は
  出典の部品（`RuleGuideDisclaimer`）の中だけで使い、本文では使わない

### 3-3. 断り書きを型で必須にする

書き忘れを人の注意力に頼らない。

```ts
/** 解説ページ1枚ぶん。断り書きは省略できない */
export interface GuidePage {
  /** …略… */
  /** このページの断り書き。`omit` を選べないので、書き忘れると型で落ちる */
  disclaimer: GuideDisclaimer
}
```

`GuideDisclaimer` は「個人が作ったものである」「正式な判断は公式の規則集による」の2点を必ず出す部品。
文言は `messages/rule_guide/<言語>.json` に置き、全ページで同じものを使う。

| --------------------- | -------------------------------- | ---------------------------- |

## 5. URL と階層

3層まで。それ以上深くしない。パスは既存ページと同じ**英語のスネークケース**（`/background_music/` `/decorating_apparatus/` に揃える）。

```text
/rules/                          入口。男子新体操とは何か。どこから読むかを示す
├── /rules/basics/               そもそもどんな競技か（団体5人・個人4手具・徒手）
├── /rules/score/                点はどう決まるか   ← B の本命
│   ├── /rules/score/difficulty/ 難度（D）とは      ← C の本命
│   ├── /rules/score/artistry/   構成・芸術（A）とは
│   ├── /rules/score/execution/  実施（E）とは
│   └── /rules/score/deduction/  減点とは
├── /rules/group/                団体（5人）のルール
│   └── /rules/group/formation/  隊形移動とは       ← A の本命・検索需要最大
├── /rules/individual/           個人のルール
│   └── /rules/individual/apparatus/ 手具4種（スティック・リング・ロープ・クラブ）
├── /rules/toshu/                徒手体操とは       ← A の本命・検索需要2位
└── /rules/words/                用語集（索引）
    └── /rules/words/<slug>/     語ごとのページ
```

### 5-1. 決めたこと

- **`/rules/` を残す。** すでに順位6.88位・CTR 6.25% の実績があるURLを捨てない
- **`/words/` を独立させず `/rules/words/` に置く。** 用語と解説書が別系統に分かれると、
  内部リンクが散って両方弱くなる。1つの体系にまとめる
- **用語ページの slug は検索語に合わせる。** 日本語の語から英語のslugを [glossary-ja-en.md](../../imrg-hub/knowledge/language/glossary-ja-en.md) で引く。隊形移動なら `/rules/words/formation_change/`
- 階層の親は必ず**子の一覧を持つ**。孤立ページを作らない。カレンダー詳細321件が孤立して弱いままになっている失敗を繰り返さない

### 5-2. 各ページが必ず持つもの

|                  | 中身                                                     |
| ---------------- | -------------------------------------------------------- |
| 答え             | **最初の3行で言い切る。** 検索から来た人は答えだけ欲しい |
| 深掘りへのリンク | 下の層への導線                                           |
| 上へ戻るリンク   | パンくず                                                 |
| 断り書き         | → 3-3                                                    |
| 動画の枠         | あれば埋め込む（→ 10）                                   |

## 6. 文章の決まりごと

「小学生でも分かる」を**人の頑張りに任せない。** 機械で測れるものは機械に測らせる。

### 6-1. 書き方

- **1文は40字まで。** 超えたら2文に割る
- **小学校で習わない漢字は開く。**「かつ」「ほとんど」「おおむね」→「かつ」「ほとんど」「だいたい」
- **専門用語は初出で必ず言い換えを添える。**「徒手（手具を持たない演技）」
- **数えられるものは表にする。** 文章で列挙しない
- **「である」ではなく「です・ます」。** 読者は子どもと保護者
- **結論から書く。** 前置き・経緯を先に書かない

### 6-2. textlint に足すルール

ルート [.textlintrc.json](../.textlintrc.json) に足す。CIの `verify` で落ちるようにする。

```jsonc
{
  "rules": {
    // 1文の長さ。40字を超えたら落とす
    "sentence-length": { "max": 40 },
    // 小学校で習わない漢字を検出する
    "ja-no-mixed-period": true,
    // 同じ助詞の連続（既に有効）
    "no-doubled-joshi": true,
    // 難しい言い方を検出する
    "ja-no-redundant-expression": true,
  },
}
```

- 対象は `web/src/entities/ruleGuide/**` と `web/messages/rule_guide/**`
- **既存のコードや他のページには効かせない。** 解説ページだけ厳しくする

### 6-3. 表は「自分の切り口」で組む

冊子の表をそのまま再現できない（→ 3-1）。だから**読者の知りたい順に組み直す。**

| 冊子の並び                      | このサイトの並び                           |
| ------------------------------- | ------------------------------------------ |
| 難度の記号ごと（A・B・C・D・E） | **やさしい順・できるようになる順**         |
| 徒手系／転回系の章で分離        | **1つの技から、何が積めるか**でまとめる    |
| 節番号つきの一覧                | **「何を見ればすごいと分かるか」**を添える |

組み直しの元ネタは、すでに自分の言葉で書いてある
[knowledge/competition/](../../imrg-hub/knowledge/competition/) の5本を使う。

## 7. 原稿の置き場所と形

### 7-1. 新しい場所に作る。いまの `entities/rule/` は使わない

```text
web/src/entities/ruleGuide/       ← 新設。自分で書いた解説
├── model/
│   ├── guidePage.ts              ページ1枚の型（断り書きを必須にする）
│   ├── guideBlock.ts             見出し・段落・表・図の枠・動画の枠
│   └── guideTree.ts              URL の木（唯一の正。ここに無いページは作れない）
├── api/
│   ├── content/ja/               日本語の本文（正）
│   ├── content/en/               英語（以下、言語ごと）
│   └── figures/                  図のデータ
└── lib/
    ├── fingerprint.ts            訳の追従を見る（既存の仕組みを流用）
    └── buildGuide.ts             ページを組み立てる
```

`entities/rule/`（条文）とは**混ぜない**。名前で区別がつく状態を保つ。

### 7-2. 本文は Markdown ではなく構造化データで持つ

Markdownの方が書きやすいが、**8言語 × 訳の追従を型で守れなくなる**。
既存の `fingerprint` と `translationStatus` の仕組み（日本語が変わったとき訳の古さを検出する）を
そのまま流用できるTSを選ぶ。

```ts
/** 本文の1ブロック */
export type GuideBlock =
  | { kind: 'lead'; text: string } // 最初の3行の答え
  | { kind: 'paragraph'; text: string }
  | { kind: 'table'; caption: string; columns: string[]; rows: string[][] }
  | { kind: 'figure'; figureKey: FigureKey; caption: string } // 絵は後から入れる（→ 8-2）
  | { kind: 'video'; videoId: string; caption: string } // YouTube（→ 10）
  | { kind: 'link'; to: GuideKey; label: string } // 深掘りへ
```

## 8. 1つの原稿から3つの出口へ

同じ本文から、**サイト・本・動画の台本**を出せる形にしておく。あとで作り直さない。

| 出口       | どう出すか                                                                      |
| ---------- | ------------------------------------------------------------------------------- |
| サイト     | `GuideBlock` をそのまま描く（いま作るもの）                                     |
| 本の原稿   | `GuideBlock` → Markdown / テキストに落とすスクリプトを書く。1ファイル増えるだけ |
| 動画の台本 | `lead` と `table` だけ抜き出せば、60秒ショートの原稿になる                      |

**本を何で作りどこで売るかは、まだ決めなくてよい。** 原稿が構造化されていれば、
あとから紙・電子・どちらにも出せる。**先に決めるのは原稿の形だけ。**

### 8-2. 図は枠だけ先に作る

- `figureKey` を本文に書いておき、**絵が無い間は枠ごと出さない**。「図は準備中」を出すと信頼を落とすので、文章だけで完結させる
- 絵は**自分の映像から描く**。冊子は見ない（→ 3-1）
- 既存の棒人間の**仕組み**（`StickPose`・コマ送り・`poseOf`・`sequenceOf`）は
  自作なのでそのまま使える。捨てるのは座標（`STICK_SKELETONS`）だけ

### 9-1. なぜ vendor/ なのか

imrg-platformは **PUBLIC**（2026-09-17に公開）。
`PUBLIC_RULES_PUBLISHED=false` で画面は閉じているが、**ソースコードは誰でも読める。**

imrg-hubはgit remoteを持たないローカル専用で、`vendor/` は `.gitignore` 済み。
[repo-structure.instructions.md:27](../../imrg-hub/.github/instructions/repo-structure.instructions.md#L27) の
「`vendor/` — 学習済みモデル・**他者の著作物**（git管理しない）」がそのまま当てはまる。

年版ごとに分けておくと、改訂を追うのが楽になる。

```text
~/imrg/imrg-hub/vendor/rulebook/
├── 2025/    いま imrg-platform にあるものを移す
└── 2027/    次の改訂版。diff を取れば改訂箇所が一目で出る
```

### 9-2. git の履歴について

過去のコミット（`998e6e1` 以降）には条文が残る。選択肢は3つ。

|                                                       | 手間 | 副作用                                                                      |
| ----------------------------------------------------- | ---- | --------------------------------------------------------------------------- |
| a. HEAD から消すだけ                                  | 小   | 履歴からは読める                                                            |
| b. 履歴も書き換える（`git filter-repo` + force push） | 大   | force push 禁止のルールセットを一時解除する。**開いている PR が全部壊れる** |
| c. リポジトリーを private に戻す                      | 中   | GitHub Pro が必要。無料のブランチ保護ルールセットが使えなくなる             |

**まず a をやる。** 読まれた形跡はほぼ無い（過去14日の閲覧はuniques 1〜2＝ほぼ本人、fork 0、star 0）。
bは、開いているPRを片付けてからあらためて判断する。

## 10. YouTube との関係

**ページを先に作り、そのあと動画を作る。** 送り先が無い動画を作らない。

- ページの本文に `{ kind: 'video' }` の枠を持たせ、そこへ動画を埋める
- 動画の概要欄からページへ返す（相互に送る）
- 作る順は **ページ → 60秒ショート → 長尺**。
  ショートのCTRは15.79%、長尺は0.43%（実測）。**短いものから入口を作る**
- すでにある動画を先に活かす。「隊形移動は何のため？」（20:17）は
  2日で419表示・5.45位なのにクリック0。**記事から送れば拾える**

## 11. 作る順

工数は時間。**待ちがあるものは明記する。**

### 優先1 — 条文データを公開の場から外す（1〜2時間）

制約に反した状態を先に止める。作り直しの前。

1. `~/imrg/imrg-hub/vendor/rulebook/2025/` を作り、`entities/rule/api/` を移す
2. imrg-platformから条文・表・線画の座標を消す。残すものは9の表のとおり
3. `/rules/` は `ComingSoon` のまま（すでにそうなっている）
4. `pnpm run verify` を通し、`feature/*` からPR

### 優先2 — 骨組みと決まりごとを実装に落とす（4〜6時間）

**本文を書く前に器を作る。** ここを飛ばすと負債になる。

1. `entities/ruleGuide/` の型（`GuidePage` `GuideBlock` `GuideKey` の木）
2. 断り書きの部品（`RuleGuideDisclaimer`）と、型で必須にする仕掛け
3. 禁止語のテスト（→ 3-2）
4. textlintのルール追加（→ 6-2）
5. URLの木から `ROUTES` とsitemapを自動で作る（ページを足すと自動で載る形にする）

### 優先3 — 検索需要の大きい3ページを書く（各2〜3時間）

**実測で需要が確認できているものから。** 入口より先でよい。

1. `/rules/group/formation/`（隊形移動とは）… 誤記の言い換えを本文に入れる
